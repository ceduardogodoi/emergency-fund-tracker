# Workflow

**Present the diff and wait for review before committing.** A green `npm run verify` is permission to present a change, not permission to commit it. Reviewing before committing is how this codebase gets read as it is built, and it catches what the suite cannot: reviewing an already-committed diff once surfaced two comments that were simply wrong, one of which restated the exact stale assumption that had caused the bug being fixed. If a commit was made early, `git reset --soft HEAD~1` puts it back for review — save the message first.

**A new convention goes in `.claude/rules/`, not in auto memory.** Add it to the file that governs it, in its own commit, with the reason it exists — every rule here says why, because a rule whose justification has been lost is one nobody can argue with or correct. Rules in this folder are versioned with the code, reviewable, and loaded automatically; a memory is visible to one tool on one machine, and drifts silently when the thing it points at moves. Auto memory is for what is genuinely about working with this person, not about this codebase.

**Commit scopes name the task.** `feat(T058): implement calculateTarget`, referring to a task in the feature's `tasks.md`. Several tasks list them — `feat(T032-T036)` for a contiguous run, `chore(T011,T012)` otherwise. Work closing no task keeps a plain scope-less subject. Mark the task `[X]` in `tasks.md` in the same commit, so the checkbox and the history agree. Under TDD the failing-test task and the implementation task land in **one** commit, listed together — `feat(T068-T070,T075-T077)`. They cannot be separated, and trying wastes an afternoon: the pre-commit hook runs `npm run verify`, and a commit holding only the red tests fails it by definition, because those tests import modules that do not exist yet. `--no-verify` would buy commit granularity by switching off the gate Principle I calls non-negotiable, which is the wrong trade. The red phase still happens — write the tests, watch them fail for the intended reason, then implement — it just happens in the working tree rather than in the history.

**Write each story's Maestro flow with the story**, not as a batch afterwards, and run it on an Android emulator _and_ an iOS simulator before calling the story done. The flows are the only tests that run the real app on a device, so deferring them defers the whole class of bug they catch: `e2e/us1-set-target.yaml` found two on its first run, both shipped and unnoticed while every unit, integration, and component test passed. The two platforms have failed differently every time it has mattered.

**Clean up after an inspection session.** `npm run e2e:clean` removes the Maestro artifacts, which the e2e scripts write to a gitignored `.maestro-out/<platform>/` precisely so one command can. Anything from a bare `maestro test` still lands in `~/.maestro/tests/` and needs `rm -rf ~/.maestro/tests/*`; never touch `~/.maestro/deps` (the iOS driver) or `~/.maestro/sessions`, which forces a re-install. Delete throwaway flows and comparison screenshots too, and keep scratch copies in the session scratchpad rather than `/tmp`. Two days of unswept runs reached 405 MB.
