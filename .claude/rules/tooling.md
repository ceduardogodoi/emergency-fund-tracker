# Tooling and environment

**Tool configs declare their module system in the extension.** `.mjs` where the tool accepts ESM (`eslint.config.mjs`, `jest.config.mjs`), `.cjs` where it requires CommonJS (`babel.config.cjs` — babel-jest loads it synchronously and Babel's ESM path is async). Never plain `.js`, which leaves the module system implicit in `package.json`'s `type`.

**Runtimes are pinned with asdf** in a committed `.tool-versions` at the repository root. Setup starts with `asdf install`, and CI installs from the same file. Never `.nvmrc`, `nvm use`, or "install Node LTS" as a step — Principle I requires the quality gate to run identically locally and in CI, which only holds if both read one pinned file.

**After restarting the Android emulator, run `adb reverse tcp:8081 tcp:8081`** before the e2e suite. The flows open the app with `openLink: exp://127.0.0.1:8081`, and inside the emulator `127.0.0.1` is the emulator. Expo sets the reverse mapping up when it connects and an emulator restart drops it, while the dev server keeps running — so nothing looks wrong, and every flow fails on `app-root is visible` after burning the full 45-second launch timeout. Suspect it first whenever _every_ Android flow fails at launch while iOS passes; the simulator shares the host's network and is never affected.

**On iOS, a Maestro flow taps a calendar day before anything scrolls the screen.** After Maestro has scrolled a React Native `ScrollView`, its taps no longer reach the SwiftUI calendar inside it — the day is not highlighted and `onDateChange` never fires — while a finger on the same simulator works. Measured on 2026-09-26 on the contribute screen: a tap on the 3rd with no scroll registered; after `scrollUntilVisible`, taps on the 15th by label, by screen position, and on a first-row day all went nowhere, identically through `@expo/ui`'s community wrapper and our own SwiftUI composition. Android's Compose calendar takes taps after a scroll. The cause is not established. It cost several runs because it looks exactly like an app bug; suspect it whenever an iOS calendar tap fails only in a flow that scrolled first. Tap the day while the calendar's top rows are still on screen, and pick a day that stays in the past whatever the run date — the plan for T074 is the previous month's 1st, reached with the calendar's month arrow, which is not yet measured.

**After Metro reports an error, cold-start the app before trusting what it shows.** Fast Refresh sends the open app every saved file as it lands, including a file that uses something the next edit has not written yet. On 2026-10-24 Metro logged `Property 'View' doesn't exist` (a component saved a few seconds before its import) and `Unable to resolve "./store-repository"` (an import saved one command before the file it names). Both were gone from the code moments later. Later that day the Android emulator's session showed Home's error state after a seed, and its retry button did not help. A cold start, force-quitting Expo Go and reopening it through `e2e/open-app.yaml`, showed the stored fund intact and correct. A broken session from those refreshes is the likely cause, though it was not reproduced. It looks exactly like an app bug, so rule it out first: suspect it whenever a screen fails in a session that has been open through edits, and the failure does not survive a restart. When making a change across files, write a new file before the edit that imports it, so no save points at something missing.

**After changing a package that ships native code or a Babel plugin, restart Metro with `npx expo start --clear` before running anything on a device.** Metro caches every transformed file, and the cache does not notice that the plugin which did the transforming has changed version. On 2026-11-08 T161 replaced `react-native-worklets` 0.10.4 with the 0.10.1 SDK 57 pins, while a Metro started that morning kept running; every unit and component test passed, and the first device run failed at boot with "[Worklets] Mismatch between JavaScript code version and Worklets Babel plugin version (0.10.1 vs. 0.10.4)" — a version no longer anywhere on disk. Restarted with `--clear`, it booted. Whether a plain restart would have done is not measured; `--clear` is the step that is known to work. Suspect it whenever a device error names a package version that `npm ls` does not show, or the app fails at boot right after an `npx expo install`. Jest runs its own transform cache through `babel-jest`, so a green suite says nothing about what Metro is serving.

**After changing a package that ships native code, delete the native build caches before a release build.** Remove every `android/.cxx` and `android/build` folder under `node_modules`, and `android/app/build`. Gradle keeps each native module's compiled C++ there, and the cache of one module can point at another's output from before the change. On 2026-11-08 T189's first Android release build failed with "ninja: error: '…/react-native-worklets/android/build/…/libworklets.so', needed by '…/libexpo-modules-core.so', missing and no known rule to make it": `expo-modules-core`'s cache still expected the worklets build from before T161 replaced 0.10.4 with 0.10.1, and nothing rebuilt it. With the folders removed, the same command built and installed. The error names a file, not a version, so it reads like a broken package rather than a stale cache; suspect it whenever a release build fails in a module's C++ step after an `npx expo install`. It is the native side of the Metro rule above, which `--clear` does not reach. Whether iOS keeps a similar cache is not measured: its release build, run after the Android clean-up, passed first time.

**Check notification behaviour in a release build of the app, never in Expo Go.** In Expo Go the installed app is Expo Go, so the permission, the channels, and the alarms are all its own: measured on 2026-11-07, it refused Android notification channels outright, put a permission dialog of its own on top of the system's, covered buttons with banners about push, and fired a reminder left over from an earlier run in the middle of a measurement. Build with `npx expo run:android --variant release` or `npx expo run:ios --configuration Release` (`android/` and `ios/` are gitignored); each build's prebuild rewrites the `ios` and `android` scripts in `package.json` to `expo run:*`, so put them back before reviewing the diff. Read the result from the operating system, not the screen. On Android, `dumpsys notification --noredact` filtered by `pkg=com.emergencyfundtracker.app` — a match on the title alone found Expo Go's — and `dumpsys alarm` for the alarm, reading `whenElapsed` as well as `origWhen`: the emulator once showed the right date with a deadline a year away. On a `userdebug` emulator, `adb root` lets the clock move to just before the reminder is due; set `auto_time` back to 1 afterwards. On iOS the simulator runs on the host's clock, and SpringBoard logs `Deliver local notification` under the app's bundle id. A reboot on the emulator is not evidence about a phone: the emulator boots with its clock behind the host's, and the phone did not show what it did (research.md, D-013). With a phone and an emulator both attached, name the device on every `adb` (`-s`) and `maestro` (`--device`) call.
